## 2. 关键设计

### 2.1 双通道分流，成本优先

FAQ 向量命中即秒回标准答案，高频问题不产生大模型调用；RAG 只在 FAQ 判不出来时介入。
两条通道共用一套会话存储与流式协议，前端不需要区分"这是 FAQ 还是 RAG"，
只按 `sources[].type`（`faq` / `doc`）渲染同一种来源卡片。

判定顺序在 `app/services/qa_service.py`：先 FAQ，未命中或 FAQ 链路异常才转 RAG。

### 2.2 单层分块

知识库规模小（30 份文档、几百分块），500 字块 + 60 字重叠即可兼顾检索精度与语义完整，
不需要父子块 / 段落聚合这类多粒度索引。

- `.md` 用 `MarkdownTextSplitter`，尊重标题层级，不把一个小节的正文切散；
- 其它文本用自研中文递归切分器（`app/rag/splitters/`）按标点断句；
- 分块主键取内容 md5，重复入库是 upsert 覆盖，**幂等**，可以放心重跑 `scripts.ingest_kb`。

### 2.3 bge-m3 单向量检索

稠密向量（1024 维、L2 归一化）+ Milvus `IVF_FLAT` 内积检索（内积即余弦相似度），
一次召回 top-k，再用相关性下限 `min_score=0.35` 过滤：域外问题的分块被全部滤掉，
上下文为空 → 自然走"信息不足"兜底。

小库无需混合检索 / 交叉编码重排这类大规模重武器——链路短、延迟低、结果可解释。
库规模真正上来之后再引入 BM25/ES 第三路召回与重排（见第 4 节）。

### 2.4 意图路由：规则为主 + 轻量分类

- **关键词规则**（`is_domain_query` / `route_domain`）判"要不要查库、路由到哪个域"；
- **TF-IDF（字符 1-2 gram）+ 逻辑回归**（210 条标注数据离线训练）判"通用知识 / 专业咨询"，
  在线推理毫秒级、无显存开销。

两道纠偏，避免分类器误判把该查库的问题放走：用户显式选域，或判为通用但命中领域关键词，
都强制走检索。`models/intent_clf.joblib` 缺失时自动退化为纯关键词规则，服务照样能跑。

### 2.5 多轮会话

历史按 `session_id` 存 MySQL `chat_turn` 表，取最近 5 轮拼进提示词
（轮数在 `app/infra/mysql.py` 的 `limit` 默认值里，未做配置项）。
清空会话走软删除，保留数据资产便于后续分析。

### 2.6 JWT 鉴权

单账号设计（内部工具，不做用户表与注册）：`/auth/login` 签发 HS256 token，
REST 走 `Authorization: Bearer`，WebSocket 走 `?token=`（握手阶段无法自定义请求头），
过期或无效分别返回 401 / 4401。密钥与口令支持环境变量注入，默认值为开发占位。

### 2.7 全链路降级

| 故障点 | 行为 | 代码位置 |
| --- | --- | --- |
| FAQ 检索异常 | 转 RAG 通道 | `app/services/qa_service.py` |
| 向量检索异常 | 返回空分块，继续走"信息不足"生成 | `app/rag/pipeline.py` |
| 意图模型文件缺失 | 退化为关键词规则 | `app/rag/intent.py` |
| 生成模型异常 | 重试 3 次（仅在零 token 时），最终给人工兜底话术 | `app/rag/pipeline.py` |
| 未配置 API Key | 启动打印告警，FAQ 通道仍可用 | `app/conf/settings.py` |
| 无 GPU | `device=auto` 回退 CPU 并关闭 fp16 | `app/infra/vector_index.py` |
| MySQL 建库权限不足 | 跳过建库并记日志，会话表按需自建 | `app/infra/mysql.py` |

**流式重试的关键约束**：一旦已经吐出过内容就绝不重试，否则前端会收到重复答案。
这也是重试次数判断放在"是否产出过 token"之后而不是捕获异常就重跑的原因。

## 3. 性能与延迟设计

单向量召回（无 rerank）+ FAQ 向量秒回 + GPU fp16，使检索段开销很低；
**端到端延迟主要由大模型生成决定**。`config.ini [milvus]` 可调：

```ini
device = auto      # auto（有 GPU 就用 cuda）/ cuda / cpu
fp16 = auto        # auto（有 GPU 就开）/ true / false，6GB 显存建议保持 auto 省显存
embed_batch = 16   # 每次向量化/写入的分块数，显存小可调小
```

### 3.1 GPU 沙箱（可选，不污染原环境）


```bash

```

## 4. 已知限制

- 检索链路强依赖 Milvus：不可用时服务无法启动（可改为懒加载 + 只读降级）。
- 单实例部署，WebSocket 未做粘性会话；水平扩容需引入共享会话状态与连接路由。
- 单账号 JWT（内部工具够用）；多用户 / 细粒度权限需引入用户表与 RBAC。
- 意图分类器为轻量线性模型，复杂或跨域问题可能误判，靠关键词规则兜底纠偏。
- FAQ 语料目前覆盖 it / oa / hr / security 四域（80 条），而 `data/kb/` 是 7 域 30 份文档——
  finance / legal / admin 三域的问题只能走 RAG，补 FAQ 语料是性价比最高的迭代方向。
- 会话历史轮数（5 轮）写在代码默认值里，未做成配置项。
- 未做请求限流、并发连接治理与指标采集。

## 5. 扩展方向

- **检索层**：库规模增大后引入混合检索 / 重排；接入 ES 或 BM25 做第三路召回；
  按域分 collection 以便独立更新与灰度。
- **生成层**：答案引用片段高亮定位到原文段落；语义级答案缓存降低重复生成成本。
- **工程层**：请求限流、异步任务化入库（大批量文档不阻塞接口）、Prometheus 指标、
  多用户与 RBAC、会话状态外置以支持水平扩容。
- **数据层**：补齐 finance / legal / admin 的 FAQ 语料；把 FAQ 阈值与 `min_score`
  做成可按域配置的参数，用 `scripts/evaluate_ragas.py` 做回归验收。
